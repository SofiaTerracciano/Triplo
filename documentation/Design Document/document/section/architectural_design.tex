The Triplo system is designed according to a modular architecture in which the main application logic is implemented on the client side, while backend functionalities are delegated to managed services and external APIs, as illustrated in Figures 2.1 and 2.2. \\

The system separates concerns between presentation, application logic, and data management by adopting a Model–View–Controller (MVC) architectural pattern. Both the presentation layer and the core application logic are implemented within the Flutter-based applications, while remaining logically decoupled through the use of Controllers that mediate between Views and Models. \\
In particular, the mobile application represents the main client, while the smartwatch application provides a lightweight extension offering a subset of functionalities adapted to the constraints and interaction model of wearable devices, relying on the same backend services and data sources.\\
User interactions are handled by the View layer, while business logic and coordination between components are delegated to Controllers, which act as the central mediation layer between the user interface and the underlying data models.\\
Data management and authentication are handled through Firebase services, specifically Firebase Authentication, Cloud Firestore, and Firebase Storage. The system leverages Firebase as a Backend-as-a-Service (BaaS) platform, providing managed services for authentication, data storage and user management, relying on platform-specific SDKs for access to these resources. 
The adoption of Backend-as-a-Service (BaaS) solutions enables the system to replace a traditional custom server-side layer with a more lightweight and scalable architecture. By delegating data management, authentication, and storage to managed services, architectural complexity is reduced by eliminating the need for maintaining a dedicated custom backend infrastructure.
In addition to Firebase, the system integrates external third-party services (e.g., weather, map, and satellite APIs), which are accessed via RESTful APIs over HTTPS. \\
This architectural approach emphasizes a client-driven design, reduces backend complexity, and enables scalability by leveraging managed cloud services.

The high-level component diagram provides an overview of the main architectural elements of the system and their interactions. The system is composed of two client applications, namely the smartphone application and the smartwatch application, both relying on a shared set of backend services and external resources. \\
The graphical user interfaces (GUIs) are represented following the convention adopted in both the \textit{Software Engineering} and \textit{UML Distilled} books quoted in the references. In this context, each GUI represents a group of related pages or a major functional area of the application, rather than a single page. \\
The diagram highlights the presence of two versions of the application. The smartphone application represents the main client and provides the full set of functionalities. It is implemented using Flutter, which enables cross-platform development and allows the application to run on both Android and iOS devices, as explained in section \ref{Other Design Decisions}. \\
The smartwatch application represents a lightweight extension of the system and is deployed on Wear OS, as discussed in section \ref{Other Design Decisions} .
It provides a subset of functionalities adapted to the constraints of wearable devices. \\
Both applications interact with a common set of backend services and selected external resources. In particular, both the smartphone and smartwatch applications access Firestore for data storage and Firebase Storage for media management, as well as shared external services such as OpenTopoMap for map visualization. However, the smartwatch application is intentionally restricted to a subset of services, reflecting its role as a lightweight client and the constraints of wearable devices. \\
An architectural difference regards authentication. While the smartphone application directly relies on Firebase Authentication, the smartwatch application does not perform authentication independently. Instead, it adopts a pairing mechanism based on QR code scanning. Through this process, the smartphone securely associates an authenticated user with the smartwatch by storing the corresponding identifier in Firestore. \\
This design choice provides several advantages, detailed in section \ref{Phone Smartwatch Pairing}






Access to backend resources such as Firestore, Firebase Storage, and selected external services is otherwise shared between the smartphone and smartwatch applications. The diagram explicitly shows which services are accessible from each client, clarifying the distribution of responsibilities. \\
The system also integrates multiple external services, for example map providers such as OpenTopoMap and Google Satellite View, as well as external authentication providers. Weather alert functionalities rely on both Weatherbit and a Demo Meteo Server. The latter is used exclusively for demonstration purposes, allowing the simulation of weather alerts without depending on real external conditions. \\

The operating system interfaces are modeled as platform components, Smartphone OS and Watch OS. These platforms are not accessed directly by the application; instead, access is mediated through Flutter packages that provide abstractions over native operating system services. The specific packages used to interact with such services are detailed in the diagrams of the smartphone application components, section \ref{Mobile Smartphone App component view} and of the smartwatch application components, section \ref{Mobile Smartwatch App component view}. \\
The interfaces associated with Firebase services, Firebase Authentication, Firestore, and Firebase Storage are based on the SDKs provided by the Backend-as-a-Service platform. These SDKs abstract the underlying communication mechanisms and offer a structured way to access backend functionalities, as documented in the Firebase official documentation. \\
In contrast, the remaining external interfaces, such as Weather API, Weather Alert API, Satellite API, are accessed through RESTful communication. In these cases, the application uses HTTP-based requests via Flutter libraries, handling data exchange in JSON format and performing client-side decoding. \\
The token verification API is not directly managed within the application logic but is represented the complete authentication flow. In particular, when authentication is performed through an external provider, Google, the application obtains an authentication token which is then passed to Firebase Authentication. Firebase subsequently validates this token with the external provider as part of the OAuth2-based authentication process. This additional interaction is abstracted by the SDK but is included in the diagram to provide a more accurate representation of the overall system behavior. \\

\subsubsection{View Components}

The UI of the application is organized into components that group together multiple views related to the same functionality, rather than representing isolated pages. This choice reflects how users interact with the system, as each View component encapsulates a complete feature.

The \texttt{GeoWatch Page component} includes all functionalities related to navigation and environmental awareness during a trekking activity. It is responsible for presenting weather information along the route, weather alerts, and a satellite map with meteorological layers. It also provides navigation support through compass heading, altitude, and user position.

The \texttt{Home Page component} represents the main map-based point of the application. It displays trekking routes on an OpenTopoMap layer and allows users to explore available paths geographically.

The \texttt{Trekking Page component} provides detailed information about a selected route, including a description and photos. It also allows users to access the component that handles the creation of a diary associated with the route and to save the route to their profile, the \texttt{Diary Page component}.

The \texttt{Diary Page component} handles the creation and modification of diary entries related to trekking experiences, including notes, images, and activity-related data.

The \texttt{User Profile Page component} is responsible for displaying user information, including saved trekkings, diary related, follower and following users' data.

The \texttt{Settings Page component} allows users to manage application and account settings, including profile information, security options such as password updates, smartwatch pairing, and weather notification preferences.

The \texttt{LoginRegistration Page component} manages login and registration workflows. It supports authentication via email and password, performs simple format validation operations, supports Google authentication, and password recovery.

The \texttt{Search Page component} enables users to search for other users and access their public profiles or to search for a trekking by its name.

\subsubsection{Controller components}

The controller package coordinates the application logic and mediates interactions between UI components, models, and backend services.

Domain controllers, such as \texttt{UserController}, \texttt{DiaryController}, \texttt{TrekkingController},\\ and \texttt{ChallengeController}, are responsible for handling use cases specific to their domain. They orchestrate data flow between the UI and Firebase services.

The \texttt{ServiceController} acts as a unified facade for functionalities that do not belong to an application domain defined in the model, such as access to external APIs and operating system services, reducing coupling between UI components and low-level implementations.

The \texttt{LanguageController} is responsible for managing localization and language-related logic.

\subsubsection{OSService Package components}

The OSService package contains services that directly interact with Flutter libraries responsible to communicate with system APIs and services managed by the operating system.

These include components such as \texttt{GeoService}, \texttt{PermissionService}, \texttt{MemoryService}, and \texttt{NotificationService}, each encapsulating a specific interaction with the operating system, such as location access, permission handling, local storage, and notifications.

This package isolates dependencies on external libraries and platform APIs. If a library needs to be replaced or updated, the changes are confined to the corresponding service, without affecting the rest of the application.

\subsubsection{Internet Service}

The \texttt{InternetService} is responsible for monitoring network connectivity. It periodically relies on the ServiceController to attempt connections to external endpoints (e.g., Google services). Based on the outcome, the application switches between offline and online modes, ensuring consistent behavior in varying network conditions.

\subsubsection{Background Service}

The \texttt{BackgroundService} enables the execution of tasks even when the application is not actively open, depending on operating system constraints.

It is used to perform periodic operations such as checking weather conditions and generating notifications. These tasks are scheduled through the mechanisms WorkManager mechanism, a Flutter wrapper around Android's Workmanager and iOS Background tasks. Background tasks are executed based on system availability.

\subsubsection{AuthService}

The AuthService is responsible not only for authentication but also for managing the smartwatch pairing process.

It handles user authentication through Firebase Auth and Google, password reset, session management, coordinates the pairing workflow between the smartphone application and the smartwatch, centralizing all identity-related logic.

\subsubsection{Backend and External Services}

The application relies on Firebase as a Backend-as-a-Service, including Authentication, Firestore, and Storage.

External services are used for specific functionalities, such as OpenTopoMap for map visualization, OpenWeather and Weatherbit for weather data and alerts, and Google services for authentication and connectivity verification.

\subsubsection{Architectural Summary}

The architecture is organized in packages that separate concerns clearly. Domain controllers manage application logic and backend interaction, the ServiceController provides a unified access point to external and system services, and OSService components encapsulate platform dependencies. This structure improves modularity, maintainability, and adaptability of the system.

Domain controllers, such as \texttt{UserController}, \texttt{DiaryController}, \texttt{TrekkingController}, and \texttt{ChallengeController}, are responsible for coordinating the application logic related to their respective functional domains. These controllers manage interactions between the View layer and the Model layer, and they also mediate access to backend resources such as Firebase services.










Therefore, in the proposed architecture:
\begin{itemize}
    \item domain controllers manage the application use cases and the interaction with Firebase-related resources;
    \item The ServiceController acts as a unified facade aggregating multiple underlying services, including external APIs (weather, maps) and device-level services (location, permissions, navigation)
    \item Firebase is modeled as a set of backend services used by the application, rather than as a custom backend.
\end{itemize}

\textbf{Note:} the GeoWatch component lightly depends on the InternetService to determine the current connectivity state, only the \textit{Navigation Page} with the compass and altimeter depends on it just for hiding the drawer menu in offline mode. This interaction is not based on direct method invocation, but the InternetService exposes a boolean connectivity state, which is observed by the UI through a provider-based mechanism. When the connectivity status changes, the service notifies listeners, and the UI updates accordingly. Since it is not a method invocation,  this has not been modelled as an interface but just as a light dependency with a dashed line in the diagram.

\subsubsection{Navigation Page Disambiguation}

The term \textit{Navigation Page} is used in both the smartphone and smartwatch applications, but it refers to different UIs with distinct responsibilities.
In the smartphone application, the Navigation Page corresponds to a view within the \texttt{GeoWatchPage} component. It provides sensor-based navigation functionalities, such as compass orientation and altitude information, supporting the user during outdoor activities.
In the smartwatch application, the Navigation Page is a standalone component (\texttt{NavigationPage}) that acts as a central access point for the main features of the wearable app. It allows the user to navigate to the Home Page, User Page, and language-related functionalities, serving primarily as a presentation hub.
This distinction is important to avoid ambiguity when referring to navigation-related components across the two platforms.

\section{Firebase BaaS Management}
\label{Firebase BaaS Management}
Immagine Database \\

The database adopted for the Triplo application is based on a NoSQL approach using Firebase Firestore. Unlike traditional relational databases, Firestore stores data as collections of JSON-like documents, where each document can contain nested structures and arrays. \\
For documentation purposes, the database structure has been represented using a diagram similar to a relational schema. This representation has been introduced for clarity and readability, allowing an easier understanding of entities and their relationships, even though the underlying data model is document-oriented rather than relational. \\
The main collections include user, diary, trekking, challenge, and auxiliary collections such as user\_index and trekking\_index, which are used to support efficient search operations. Additional collections such as watch, watch\_pair, and weather\_notification handle device pairing and notification functionalities. \\
From an infrastructure perspective, the Firestore database is deployed in the \textit{europe-west 8} region, while Firebase Storage is currently hosted in the United States. This configuration may introduce additional latency when retrieving large media assets such as images. A potential improvement would be to migrate storage resources to a European region, which is supported by Firebase through paid plans, in order to reduce latency and improve performance. \\
To mitigate latency issues, especially for images retrieved from Firebase Storage, a caching strategy has been adopted. Some images are locally cached on the device, reducing repeated network requests and improving user experience. This design decision is further discussed in Section~\ref{Image cache design decision}. \\

In particular, the diagram distinguishes the mobile deployment on Android and iOS devices, while the smartwatch deployment is limited to Wear OS. 
The cloud side is modeled as a device containing different execution environments, namely Firebase and the set of external providers, which host the artifacts used by the applications.






The deployment diagram represents the distribution of the application artifacts across different execution environments. In particular, the smartphone application is deployed as an artifact on both iOS and Android execution environments, while the smartwatch application is deployed separately on a Wear OS execution environment.

Although the smartphone application is shown as deployed on two distinct platforms, it is important to note that it is based on a single shared codebase. The application is developed using Flutter, a cross-platform framework that allows the same source code to be compiled and executed on both iOS and Android devices. As a result, the two deployments correspond to different execution environments of the same application, rather than distinct implementations.
In contrast, the smartwatch application is implemented as a separate artifact. While it shares the same backend services and part of the architectural structure, it is specifically designed for the Wear OS environment and provides a reduced set of functionalities for wearable devices. Therefore, it is represented as a distinct deployment unit in the diagram.

\subsection{Add Diary Page use case sequence diagram} 
\label{Add Diary Page use case sequence diagram}
The most important part of the \textit{Add Diary Page} sequence diagram is the save phase, where the data entered by the user is stored in the system.
When the user presses the save button, the \texttt{DiaryPage} starts the process by showing a loading page and then it formats the date, computing the duration from hours and minutes. If the user has selected photos, the page calls the \texttt{DiaryController} to upload them to \texttt{FirebaseStorage}. The controller uploads each image and returns a list of paths, which will be stored in the diary instance. \\
After this step, the \texttt{DiaryPage} calls the \texttt{addDiary()} method of the \texttt{DiaryController}, passing all the collected data. The controller retrieves the current user identifier from \texttt{FirebaseAuth}, generates a new unique identifier for the diary, and creates a \texttt{Diary} object. \\
Before saving the diary in \texttt{FirebaseFirestore}, the object is converted into a \texttt{Map<String, dynamic>}. This is necessary because Firestore stores data in a JSON-like format, which is based on key-value pairs. The map represents the diary as a set of fields (such as date, duration, notes, etc.), where each field is associated with a value. The type \texttt{dynamic} is used because these values can have different types, such as strings, numbers, booleans, or lists. \\
Once converted, the map is stored in the \texttt{diary} collection in Firestore. At the same time, the controller updates the user document, adding the diary identifier to either the public or private diary list, depending on the selected visibility. \\
Finally, the control returns to the \texttt{DiaryPage}, which updates the user level through the \texttt{UserController} and navigates to the \texttt{UserPage}, completing the operation.  \\

\subsection{View Trekking Information Sequence Diagram}
The sequence diagram for the \textit{View Trekking Information} use case describes how the system presents the details of a selected trekking. The interaction starts when the user opens the \texttt{trekkingPage}. The page initializes its internal state and verifies which user is authenticated through the \texttt{UserController}. \\
The trekking data is then retrieved through the \texttt{trekkingController}. In particular, the controller attempts to search in its local collection. \\
After the trekking has been obtained, the page checks whether the route is already saved by the current user. \\
The page also requests weather information near the trail through the \texttt{servicecontroller}.  \\
A further part of the interaction regards the trekking images, such as the map photo, the ending point photo, and the challenge images. In the main sequence diagram, this step is represented at a high level through calls from the \texttt{trekkingPage} to the \texttt{trekkingController}. The detailed behavior of the cache mechanism used for image retrieval is described separately in a separate diagram, in order to keep the main diagram focused on the overall interaction flow. \\
Finally, the page allows the user to perform additional actions related to the trekking. The route can be saved or removed from the saved list, a diary entry can be created through the \texttt{DiaryPage}, and the user can navigate to other trekking-related views such as the route details page or the geowatch and map page. In this way, the \texttt{trekkingPage} acts as the central entry point for the main information and actions associated with a trekking.  \\



\subsubsection{Image Caching for Trekking Images Sequence Diagram}
\label{Image Caching for Trekking Images Sequence Diagram}
This sequence diagram illustrates, through a representative example, how the image caching mechanism is implemented within the application. Its purpose is not to introduce a new use case, but rather to clarify the internal behavior of image retrieval, which is abstracted in the main sequence diagram describing the trekking visualization flow. \\
The process starts when the \texttt{trekkingPage} requests an image through the \texttt{trekkingController}. The controller delegates the retrieval to the \texttt{memoryservice}, which implements a multi-level caching strategy. \\
First, the system attempts to retrieve the image from the in-memory RAM cache, using a \texttt{Map<String, File>} structure. If the image is found, it is immediately returned to the page, ensuring minimal latency. \\
If the image is not available in memory, the system checks the disk cache through the \texttt{CacheManager}. This involves interacting with the underlying operating system to load a previously stored file. If the image is found on disk, it is reinserted into the in-memory cache and returned to the UI, improving performance for subsequent accesses. \\
If the image is not available in either RAM or disk cache, the system performs a download from \texttt{FirebaseStorage}. In the case of paths expressed using the \texttt{gs://} protocol, the controller first resolves them into a downloadable URL. The image is then downloaded, stored on disk, and finally cached in memory before being returned to the page. \\
The same logic is applied in a batched manner when multiple images, for example trekking challenges, are requested. In this case, the controller iterates over all image paths and applies the same caching strategy to each element. \\

\subsection{View Weather Information Sequence Diagram}
\label{View Weather Information Sequence Diagram}
The \texttt{Geowatch} component is responsible for retrieving, processing, and displaying weather information related to a trekking route or the user’s current position. This functionality is implemented through the \texttt{ServiceController}, which acts as a facade for external APIs.
The main logic is handled by the method \texttt{\_loadAll()}, which is responsible for orchestrating the full weather retrieval process. This method:
\begin{itemize}
    \item determines the target location (trekking route or user GPS position),
    \item retrieves current weather data,
    \item retrieves forecast data,
    \item parses the forecast into a simplified structure,
    \item retrieves weather alerts.
\end{itemize}
The method is invoked:








\begin{itemize}
    \item once during initialization,
    \item periodically through a timer (every 5 minutes),
    \item when the user switches between trail-based and GPS-based weather.
\end{itemize}
The method \texttt{\_loadAlertState()} is responsible for retrieving the current notification status for the selected trekking route. It queries the \texttt{TrekkingController}, which:

\begin{itemize}
    \item retrieves the current user identifier through \texttt{AuthService},
    \item queries Firestore to check whether the trekking is present in the user’s alert list.
\end{itemize}
The result determines the state of the notification icon in the UI.
The method \texttt{weather(lat, lon, lang)} performs an HTTP request to the OpenWeather API. The JSON response is decoded into a \texttt{Map<String, dynamic>} and sent over to the UI.
The method \texttt{forecast(lat, lon, lang)} retrieves raw forecast data from OpenWeather. Since the response contains multiple time-based entries, a parsing phase is required.
This parsing is handled by the following methods in the \texttt{ServiceController}:










\begin{itemize}
    \item \texttt{parseForecastItem(raw)}: converts a single raw JSON entry into a simplified structure (date, temperature, icon, description),
    \item \texttt{parseForecast(rawList)}: applies the transformation to all entries.
\end{itemize}


Weather alerts are obtained from two sources:
\begin{itemize}
    \item \texttt{weatherbitAlerts(lat, lon)} for real-time alerts,
    \item \texttt{mockAlerts()} for testing purposes.
\end{itemize}

The results are merged within the UI layer to provide a unified alert visualization.
The \texttt{GoogleSatellitePage}, part of the \texttt{Geowatch} component, provides an alternative map visualization using satellite imagery. The page retrieves tile URLs through the \texttt{ServiceController} and optionally overlays weather layers, such as pressure, rain and others using OpenWeather tile services.
Weather data is handled using \texttt{Map<String, dynamic>} structures. This allows flexible interaction with JSON responses, avoiding the need for rigid model definitions.





\paragraph{Handling Asynchronous Updates in Dynamic Pages}
The \texttt{mounted} property indicates whether the current page is still visible and active.
When a page is removed (for example, after navigating to another screen), it is no longer safe to update its UI.

Since weather data is loaded asynchronously, it may happen that:
\begin{itemize}
    \item a request is started,
    \item the user leaves the page,
    \item the request completes afterward.
\end{itemize}

If \texttt{setState} is called after the page has been removed, the application would crash.

For this reason, the code checks \texttt{if (!mounted) return;} before updating the UI,
ensuring that updates are performed only when the page is still active.




\paragraph{Google Satellite integration}
The Google Satellite page does not directly perform HTTP requests to OpenWeather.
Instead, it delegates the construction of the tile URL to the ServiceController.



The base map is not a single image but is composed of multiple small image tiles.
The ServiceController provides a URL template for the map provider, for example Google Satellite for Geowatch or OpenTopoMap for the HomePage.

This URL contains placeholders such as \texttt{\{z\}}, \texttt{\{x\}}, and \texttt{\{y\}}, which represent:
\begin{itemize}
    \item the zoom level (\texttt{z})
    \item the horizontal tile index (\texttt{x})
    \item the vertical tile index (\texttt{y})
\end{itemize}

The map component replaces these placeholders and loads only the tiles needed
for the current view. When the user moves or zooms the map, new tiles are requested dynamically.

\paragraph{Architectural Separation: UI and API Responsibilities}
The UI does not directly perform HTTP requests for weather data.
Instead, it delegates all external API interactions to the ServiceController.

An exception is the map rendering system, for both this map and the map in the home page, sequence diagram \ref{Explore Trekkings on Map Sequence Diagram}: once a tile URL template is provided,
the map component internally handles tile requests to external providers.
This behavior is part of the rendering library FlutterMap and does not violate the architectural separation,
as the application logic does not manage these requests.

\subsection{View Compass and Altitude Information Sequence Diagram}

The \texttt{Geowatch} component is responsible for displaying compass, altitude, and current position information. This functionality is implemented through the interaction between the page, the \texttt{servicecontroller}, the \texttt{geoservice}, and the \texttt{permissionservice}.
When the navigation page is opened, the initialization starts in \texttt{initState()}, where the page registers itself as an app lifecycle observer and schedules the execution of \texttt{\_initLocation()}. The observer is used to detect when the application returns to the foreground, for example after the user has changed GPS or permission settings.
The method \texttt{\_initLocation()} delegates the preliminary checks to the \texttt{servicecontroller} through \\ \texttt{loadNavigationLocation()}. This method verifies whether the location permission has been granted and whether the GPS service is enabled. If one of these conditions is not satisfied, the page enters an error state and shows a dedicated message to the user.
If permission is denied, the returned state contains the error \texttt{PERMISSION\_DENIED}. If the GPS service is disabled, the returned state contains the error \texttt{GPS\_DISABLED}. In both cases, the page updates its local state through \texttt{setState()} and displays an error instead of the navigation information.
Only when both checks are successful does the page subscribe to the position stream. The stream is obtained through the \texttt{servicecontroller}, which delegates the request to the \texttt{geoservice}. Every new \texttt{Position} object received from the stream is used to update altitude, latitude, longitude.
The compass information is handled through a separated stream. In the architecture, the UI does not access the \texttt{FlutterCompass} library. Instead, it requests the compass stream through the \texttt{servicecontroller}, which delegates the operation to the \texttt{geoservice}. The UI then receives heading values and converts them into cardinal directions through the helper method \texttt{\_direction()}.
When an error state is shown, the page also provides a button that helps the user solve the problem. If the GPS is disabled, the button invokes \texttt{openGpsSettings()}, which is delegated through the \texttt{servicecontroller} to the \texttt{geoservice}. If the problem is related to permissions, the page instead invokes \texttt{openPermissionSettings()}, which is delegated to the \texttt{permissionservice}. In this way, the UI does not directly interact with operating system APIs.
The diagram also includes the handling of lifecycle changes. When the app returns to the foreground, it handles the app state change through method \texttt{didChangeAppLifecycleState()}. The page sets the checking state again and re-runs \texttt{\_initLocation()}. This is useful, for example, when the user comes back from the system settings after enabling GPS or granting permissions.
Finally, when the page is closed, the observer and the active position stream subscription are disposed through the \texttt{dispose()} method. This avoids unnecessary updates when the page is no longer visible.

\subsubsection{Application Lifecycle in Flutter}

The \textbf{application lifecycle in Flutter} refers to the sequence of states an app goes through during its execution, such as \textit{resumed}, \textit{inactive}, \textit{paused}, and \textit{detached} and the mechanisms provided to handle transitions between these states.
Flutter provides a platform-independent abstraction of the lifecycle through the \texttt{AppLifecycleState} enum. Developers can monitor these changes by implementing the \texttt{WidgetsBindingObserver}, which allows the application to listen for lifecycle updates.
In particular, the method \texttt{didChangeAppLifecycleState(AppLifecycleState state)} is overridden to react to state transitions, enabling behaviors such as pausing tasks, saving data, or managing background operations when the app moves between foreground and background.












\subsubsection{Difference between permission denied and GPS disabled}
The two error conditions shown in the diagram represent different problems.
The \texttt{PERMISSION\_DENIED} state means that the application is not allowed to access the device location. In this case, the problem is related to the application permission, so the user must enable the permission from the app settings.
The \texttt{GPS\_DISABLED} state means that the application has permission to access location, but the location service of the device is currently turned off. In this case, the problem is not related to the app permission, but to the system location service, so the user must enable GPS from the device settings.
For this reason, the page provides two different actions: opening the application settings in the case of denied permission, and opening the location settings in the case of disabled GPS.

\subsection{Login Sequence Diagram}

The login process supports two authentication mechanisms: email/password and Google sign-in. These are modeled as alternative flows within the same sequence diagram.
\paragraph{Email and password login}
When the user presses the login button, the page executes the method \texttt{\_loginEmailPwd(context)}. The method first validates that both email and password are not empty. If one of the two fields is missing, the page shows an error message through a \texttt{SnackBar}.

If the input is valid, the page invokes \texttt{userController.login(email, password)}. The \texttt{UserController} delegates the operation to the \texttt{AuthService}, which uses Firebase Authentication to authenticate the user through \texttt{signInWithEmailAndPassword()}.

Firebase Authentication is used exclusively to verify user identity and retrieve a unique user identifier (UID). The method \texttt{signInWithEmailAndPassword()} returns a \texttt{UserCredential} object, which contains the authenticated Firebase user. 
After authentication, the system invokes \texttt{loadUserCore()}, which retrieves the user document from Firestore:

\begin{itemize}
\item Username
\item Email
\item Profile data
\item Level and statistics
\end{itemize}

This method intentionally avoids loading relational or large data such as followers, following, or diaries. This design prevents blocking the UI during login and improves perceived performance.

Instead, additional data is loaded lazily in the UserPage using \texttt{FutureBuilder}, enabling asynchronous and incremental UI updates.

After successful login, the application navigates to the UserPage, whose loading behavior is described in a separate sequence diagram.

\paragraph{Google login}
When the user presses the Google Sign-In button, the page executes \texttt{\_loginGoogle(context)}. The request is delegated to \texttt{userController.loginWithGoogle()}, which calls the corresponding method in the \texttt{AuthService}.

The Google login flow first forces a sign-out from the previous Google session and then opens the Google account interface. If the user does not select a profile, the flow terminates with an error message shown in the UI.

If the user selects a Google account, the \texttt{AuthService} retrieves the Google authentication tokens and exchanges them for Firebase credentials through \texttt{signInWithCredential()}. Once Firebase authentication succeeds, the service verifies whether the user already has a corresponding Firestore profile through \texttt{\_ensureUserFirestoreDocs(user)}. If the profile does not exist, the service creates the required documents in both the \texttt{users} and \texttt{users\_index} collections. After that, the method \texttt{loadUserCore(uid)} is executed, and the page navigates to the \texttt{UserPage}.

\subsection{View User Information Sequence Diagram}

The UserPage can be opened either as the landing page after a successful login or through the normal application navigation. Once the page is displayed, it retrieves the current authenticated user from the UserController.

During initialization, the page schedules the invocation of \texttt{loadTrekking()} through \texttt{Future.microtask()}, instead of calling it directly inside \texttt{initState()}. Although trekking loading is not strictly part of the core profile information, this preload can still be justified for the following reasons
\begin{itemize}
    \item the UserPage is often the first page shown after login, so loading trekking data here can anticipate work that will likely be needed shortly afterward by pages such as the HomePage, TrekkingPage, SearchPage, and the saved trekking tab itself
    \item the UserPage allows navigation toward saved trekkings and trekking detail pages, so having the trekking cache already populated may reduce subsequent loading work
    \item \texttt{loadTrekking()} acts as a warm-up step for the controller-side cache, because it populates the local \texttt{\_trekkings} list and makes data immediately available for methods such as \texttt{getTrekkingById()}, \texttt{getTrekkingId()}, using Firestore only as secondary solution

Then, for each identifier, it loads the corresponding trekking document and converts it into a \texttt{Trekking} object through \texttt{Trekking.fromMap()}.
This design combines a lightweight preload of trekking data with lazy loading of profile-related collections, keeping the UserPage responsive while still preparing application data that is likely to be useful immediately after login.

\subsection{Phone Watch Pair}
\subsubsection{High level description of the pairing mechanism}
The pairing mechanism associates a Wear OS device with an authenticated mobile user through a backend-mediated approval process. The watch does not authenticate directly with Firebase Auth; instead, device identity and user identity are linked via Firestore. Reasons behind this design decision are detailed in Section \ref{Phone Smartwatch Pairing}

\subsubsection{Device Identity}
Each watch either makes or restores from memory a \texttt{watchId}, stored securely on-device.  
A corresponding document exists in Firestore:
\begin{verbatim}
watch/{watchId}
\end{verbatim}
The \texttt{watchId} uniquely identifies the physical device and is never deleted during logout.
\subsubsection{Pairing Flow}
\textbf{1. Initialization (Watch)}  
The watch provides a new random UUID (\texttt{qrToken}) and writes:









\begin{verbatim}
watch_pair/{watchId}
\end{verbatim}
with:
\begin{itemize}
    \item \texttt{status = "waiting"}
    \item \texttt{uid = null}
    \item \texttt{qrToken}
    \item \texttt{createdAt}, \texttt{expiresAt}
\end{itemize}
A QR code encoding \texttt{watchId} and \texttt{qrToken} is displayed.
URI format: \\
\texttt{triplo://watch-pair/<watchId>?t=<token>}\\ 

\textbf{2. Approval (Phone)}  
After scanning the QR, the authenticated mobile app:
\begin{itemize}
    \item Verifies token validity and expiration.
    \item Updates the document with:
    \begin{itemize}
        \item \texttt{status = "approved"}
        \item \texttt{uid = request.auth.uid}
    \end{itemize}
\end{itemize}




\textbf{3. Completion (Watch)}  
The watch listens to the document in real time.  
When \texttt{status == "approved"} and \texttt{uid} is set, pairing is considered complete and the watch loads user data using that \texttt{uid}.
\subsubsection{Session Restoration}
On startup, the watch checks:
\begin{verbatim}
watch_pair/{watchId}
\end{verbatim}
If the document is already approved, the session is restored.
\subsubsection{Logout}
Logout does not delete the device identity. Instead, the watch resets:
\begin{itemize}
    \item \texttt{status = "waiting"}
    \item \texttt{uid = null}
\end{itemize}
This preserves device identity while removing user association.
\subsubsection{Security Properties}
\begin{itemize}
    \item Only the watch may create/reset pairing in \texttt{waiting} state.
    \item Only authenticated users may approve pairing.
    \item QR tokens are random and time-limited.
    \item The smartphone application allows the user to remotely disable or re-enable an existing pairing through a backend flag
\end{itemize}
This design cleanly separates device identity from user authentication while minimizing credential exposure on the wearable device.






\subsubsection{Remote Pairing Management and Anti-Theft Property}

The system provides a remote management mechanism that allows users to enable or disable the usability of a paired wearable device directly from the smartphone application.
Instead of removing the association between the user and the device, the system maintains the pairing information in the backend and relies on a dedicated status flag to control whether the pairing can be effectively used by the watch.
If the pairing is disabled, the wearable device cannot access or display the associated user profile. However, the underlying association remains stored in the backend.
If the pairing is re-enabled, the wearable device regains access to the associated user profile without requiring a new pairing procedure.
This design introduces an anti-theft and safety property: in case of device loss or unauthorized access, the user can quickly disable the pairing, effectively blocking access to personal data while preserving the association for future recovery.

\subsubsection{Phone-side smartwatch pairing approval from the SettingPage component}
\textit{Phone-side smartwatch pairing sequence diagram} illustrates the phone-side portion of the smartwatch pairing. In the phone UI implementation, the QR scanning interaction belongs to the \texttt{SettingPage} component.  \\
The interaction starts when the user opens the pairing section and scans the QR code on the smartwatch. Once a QR code is detected, the page extracts the raw payload and checks if that code has already been processed. This behaviour is handled by the boolean flag \texttt{\_handled}. \\
This flag is used to not allow repeated processing of the same scanner detection while the page is still active. \\
If a valid raw payload is available, \texttt{SettingPage} delegates the parsing step to \\\texttt{UserController.extractWatchPair()}, which delegates the actual logic of the phone side pairing process to \texttt{AuthService.extractWatchPair()}. This service parses the scanned URI and verifies that it matches the following structure: \\
\texttt{triplo://watch-pair/<watchId>?t=<token>}\\ 
The service also validates the presence of both the smartwatch identifier and the temporary QR token in the URI payload. If the payload is malformed, the page shows an error message and enables a new scan by resetting \texttt{\_handled}. \\
If the QR payload is valid, the page shows a confirmation dialog to the user. If the user does not confirm the operation, the page allows the next scan. If the user confirms, the page invokes \texttt{UserController.approveWatchPair()}, which forwards the request to \texttt{AuthService.approveWatchPair()}. \\
The actual approval is performed inside \texttt{AuthService}, since this step depends on the currently authenticated phone user and on the pairing state stored in Firestore. The service executes a Firestore transaction on the document \texttt{watch\_pair/<watchId>}. The transaction reads the document snapshot, denoted as \texttt{snap}, and validates the pairing request by checking four conditions: the document must exist, its status must be \texttt{waiting}, the token stored in Firestore must match the token contained in the scanned QR code, and the expiration timestamp must still be valid. \\
Only if all these conditions hold, the transaction updates the pairing document by setting \texttt{status = approved} and by storing the UID of the authenticated phone user. From an architectural perspective, the transaction is important because it makes validation and approval atomic. This reduces the risk of inconsistent state transitions. The page itself does not directly interact with Firestore or Firebase Authentication; it only reacts to success or failure by updating local UI state. \\











\subsubsection{Watch bootstrap and initialization of the pairing-aware user flow}
When the smartwatch application starts, it first executes a lightweight bootstrap phase whose purpose is to restore a stable device identity and initialize the user-related flow in a pairing-aware way, as illustrated in the \textit{Watch bootstrap sequence diagram}. This bootstrap does not directly perform the pairing itself, but it prepares the conditions under which the pairing logic can later determine whether the watch should show the QR-based login screen or the actual user area.
The first relevant step regards the retrieval of the watch identifier. During application startup, the watch obtains a \texttt{watchId} through \texttt{WatchIdService.getOrCreateWatchId()}. If a valid identifier is already available in secure local storage, that value is reused. Otherwise, the application makes or retrieves a new identifier and stores it locally so that the same watch can be recognized across future executions. This mechanism ensures that the pairing protocol is tied to a stable device identity.
Once the \texttt{watchId} is available, the application initializes the services and controllers involved in the watch-side user flow. In particular, \texttt{PairingService} is created with the current \texttt{watchId}, while \texttt{UserController} is connected to the pairing service so that it can later load the profile corresponding to the paired user. The entry point for the user-related interaction is not the pairing screen itself, but \texttt{NavigationPage}. When the user selects the user area from the navigation menu, the application pushes \texttt{PairingGateway(child: UserPage())}.
At this point, \texttt{PairingGateway} performs the bootstrap of the pairing route.

\subsubsection{Watch-side access to the user area through the pairing flow}
\textit{Watch-side smartwatch pairing sequence diagram} describes how the smartwatch application grants access to the user area through the pairing mechanism. In the watch app implementation, the user does not open a pairing screen, the interaction starts from \texttt{NavigationPage}: when the user taps the \texttt{User} button, the application performs a \texttt{Navigator.push()} toward \texttt{PairingGateway(child: UserPage())}. \\


\subsubsection{Pairing Gateway}
From an architectural perspective, \texttt{PairingGateway} should not be interpreted as an autonomous functional component, it is considered part of the PairingService and its role is to decide whether the watch should render the QR-based pairing screen or the actual \texttt{UserPage}. \\
The pairing bootstrap starts in the state of \texttt{PairingGateway}, which is the widget pushed when the user opens the user area from \texttt{NavigationPage}. Its responsibility is not to implement the pairing itself, but to bootstrap the pairing state and decide which page should be rendered, either the \texttt{LoginPage} or \texttt{UserPage}. \\

\subsubsection{Restoring the session if the user has already paired the watch}
The pairing logic relies on two complementary mechanisms. First, \texttt{PairingService.restoreWatchPairing()} performs a read of the Firestore document \texttt{watch\_pair/<watchId>} in order to determine the current pairing state. Second, the service installs a real-time subscription through \texttt{docRef.snapshots().listen()}, so that later updates to the same Firestore document, such as approval from the phone or a reset to the \texttt{waiting} state, are seen by the watch without requiring to implement a more complicated ping-like mechanism to listen to updates of the document on Firestore. \\
If the pairing document is already in \texttt{approved} state and contains a non-empty UID, \texttt{PairingService} stores that UID in its internal variable \texttt{\_pairedUid} and calls \texttt{notifyListeners()}. In this context, the listeners are the Flutter widgets that observe \texttt{PairingService} through Provider, notably \texttt{PairingGateway}. \\
At this point, \texttt{PairingGateway} requests \texttt{UserController.loadCurrentPairedUser()}. This step is necessary because the pairing service only knows which user UID is associated with the watch, but it does not load the complete user profile. The actual profile loading is delegated to \texttt{UserController}, which reads the corresponding document from the \texttt{User} collection by calling \texttt{loadUserCore(uid)}. The returned Firestore snapshot, denoted as \texttt{snap}, is converted into a \texttt{User} domain object through \texttt{Users.fromMap()} and stored in \texttt{UserController} as \texttt{\_currentUser}. When \texttt{loadUserCore()} completes, \texttt{UserController} also calls \texttt{notifyListeners()}. \\
Here again, the listeners are the widgets that observe \texttt{UserController} through Provider and the \texttt{PairingGateway} is a listener. \\
Then the UI is rebuilt because the \texttt{PairingGateway} returns the widget child that was set by the \texttt{Navigation Page} through \texttt{Navigator.push()} toward \texttt{PairingGateway(child: UserPage())}. The \texttt{UserPage} is then able to see that a paired UID is available. \\
In this sense, the pairing service is responsible for determining whether the watch is associated with a user, whereas the user controller is responsible for loading the actual user data needed by \texttt{UserPage}. \\

\subsubsection{Pair the watch if the user has not paired it}
If no approved pairing is found, the \texttt{PairingService} starts a new pairing cycle through \\\texttt{PairingService.startWatchPairing()}. In this branch, the service makes a new QR token, stores it in local state, writes the Firestore document \texttt{watch\_pair/<watchId>} with status \texttt{waiting}, a null UID, an expiration timestamp, and a new token, and then installs a snapshot listener on that document. A local expiration timer is also started. The \texttt{PairingService} then renders \texttt{LoginPage}, which reads the QR payload exposed by \texttt{PairingService} and displays it to the user. The \texttt{LoginPage} is only the visual pairing screen, it does not control the pairing itself. \\
The most relevant transition regards the phone approving the QR code. This operation updates the Firestore document \texttt{watch\_pair/<watchId>} by setting its status to \texttt{approved} and assigning the corresponding user UID. The update is received by the active snapshot listener previously installed by \\\texttt{PairingService.startWatchPairing()} through \texttt{docRef.snapshots().listen()}. \\
Inside the listener, the service reads the updated document and retrieves the fields \texttt{status}, \texttt{uid}, and \texttt{qrToken}. At this point, the service compares the token stored in Firestore with the locally active token (\texttt{\_qrToken}). This comparison is performed inside the listener itself through the instruction \texttt{if (tokenOnDb != \_qrToken) return;} and ensures that only updates referring to the currently displayed QR code are accepted. If the tokens do not match, the update is ignored, in order not to approve stale QR codes. \\
If the token matches and the status is \texttt{approved}, \texttt{PairingService} stores the paired UID in \texttt{\_pairedUid}, stops the expiration timer, and calls \texttt{notifyListeners()}. This notification is sent over to the \texttt{PairingGateway}, that rebuilds the UI. The \texttt{PairingGateway} reacts to the new state by invoking \\ \texttt{UserController.loadCurrentPairedUser()}, which loads the corresponding user document from Firestore and reconstructs the \texttt{Users} model. As a result, the UI transitions from the pairing screen to \texttt{UserPage}. \\
The logout and re-pairing flow clarifies an additional architectural point. When the user logs out from the smartwatch user page, \texttt{PairingService.logoutWatch()} clears the active timer, stops the current Firestore pairing subscription, resets the pairing document by making a new QR token and restoring the \texttt{waiting} state, and clears the locally paired UID. However, the reset of the backend document alone is not sufficient, the observation of the pairing document must be reinstalled through a new call to \texttt{restoreWatchPairing()}. This step is crucial because otherwise the watch could display a new QR code while failing to display the UserPage correctly after the first approval performed by the phone. \\




\subsubsection{Phone-side management of connected watches and remote logout}

\textit{Phone-side view paired watches and remote logout management sequence diagram} describes the phone-side flow used to inspect the currently connected smartwatch devices and manage the remote logout flag associated with them. This functionality does not replace the ordinary pairing protocol; rather, it provides an additional management layer on top of the live pairing state already stored in Firestore. \\
The interaction starts from \texttt{SettingPage} component, where the user opens the dedicated paired watches page. Once the route is pushed, \texttt{PairedWatchesPage}, which is part of the \texttt{SettingPage} component requests the list of paired watches through \\ \texttt{UserController.getConnectedWatches()}, that invokes \texttt{AuthService.getConnectedWatches()}. \\ \texttt{AuthService} then queries the \texttt{watch\_pair} collection by selecting the documents whose \texttt{uid} matches the authenticated user and whose \texttt{status} is \texttt{approved}. The result is returned to the page and rendered as a list of paired smartwatch devices. \\
It is important to clarify the semantics of this page. The data shown here does not represent a historical registry of every device ever associated with the account. Instead, it reflects the current pairing state stored in Firestore, according to the active content of the \texttt{watch\_pair} documents. \\
For each listed watch, the page also provides an operation to enable or disable remote logout. These actions are again delegated through \texttt{UserController} to \texttt{AuthService}. When the user enables remote logout, the phone updates the selected \texttt{watch\_pair/<watchId>} document by writing a timestamp into the optional field \texttt{remoteLogoutAt}. When the user clears remote logout, the same field is set back to \texttt{null}. From the phone-side perspective, these operations are intentionally simple and do not alter the ordinary pairing fields such as \texttt{status}, \texttt{uid}, or \texttt{qrToken}. \\
This design choice is architecturally relevant because it keeps the original pairing protocol unchanged. The field \texttt{remoteLogoutAt} acts as an additional control flag, not as a replacement for the existing pairing state. The watch continues to observe the same \texttt{watch\_pair} document through its existing Firestore listener and may interpret the presence or absence of \texttt{remoteLogoutAt} as a condition that temporarily blocks or restores access to the user area. In this way, remote logout can be managed from the phone while leaving the main pairing flow conceptually intact. \\

In this sense, the interfaces shown in Figure~\ref{Interface Diagram Smartphone Application} contribute to preserving a clear separation between application logic and platform-dependent concerns.

More specifically, \texttt{Permission\_i} encapsulates permission requests.\\
\texttt{geo\_i} abstracts location-service availability and position streaming\\
\texttt{Notification\_i} defines the operations needed to issue local notifications \\
 and \texttt{Memory\_i} centralizes local storage concerns, including image caching, saving the preferred locale.

The diagram also contains a set of lightweight model-oriented interfaces, namely \texttt{qi}, \texttt{dmi}, \texttt{expi}, and \texttt{umi}. 
These define conversion contracts based on \texttt{toMap()} and \texttt{fromMap(...)} operations. 
Their purpose is to standardize the serialization and deserialization logic used to map application objects to and from Firestore representations. 

In addition to the previously described interfaces, Figure~\ref{Interface Diagram Smartphone Application} also includes the \texttt{authservice\_i} interface, which encapsulates the operations related to user authentication and credential management.

This interface defines a dedicated contract for handling authentication workflows, including registration, login (both with email/password and Google Sign-In), logout, password reset, and automatic session restoration.

From an architectural perspective, \texttt{authservice\_i} plays a key role in separating authentication from the higher-level domain logic exposed by \texttt{User\_i}. 
While \texttt{User\_i} provides user-related functionalities at the application level, \texttt{authservice\_i} is responsible for interacting with the underlying authentication provider (e.g., Firebase Authentication), thus centralizing all authentication-related operations in a single component.

This design choice improves modularity and maintainability, as it prevents other components from directly depending on authentication mechanisms and allows the authentication logic to be modified or extended with minimal impact on the rest of the system.

Overall, the interfaces represented in Figure~\ref{Interface Diagram Smartphone Application} document a design in which each major responsibility is accessed through a clearly delimited contract. 
This improves readability of the architecture, supports separation of concerns, and makes explicit which services are expected from each component without exposing internal implementation details. 
For these reasons, the interface view complements the component decomposition by showing not only which elements exist in the system, but also how their responsibilities are formally made available to the rest of the application.

\section{Selected architectural styles and patterns} \label{Selected architectural styles and patterns}
\subsection{Architectural Patterns: Model--View--Controller with Mediator and Observer}
\begin{figure}[H]
    \label{Overview Diagram}
    \centering
    \includegraphics[width=0.7\linewidth]{./images/modelviewcontroller.png}
    \caption{Model view controller pattern, adapted from Apple and Oracle documentation}
\end{figure}

The system adopts the Model--View--Controller (MVC) architectural pattern to separate presentation, application logic, and data management. Within this structure, each role is assigned a specific responsibility in order to improve modularity, maintainability, and clarity of interactions.

The \textbf{Model} represents the knowledge and expertise related to the application domain. It includes the core data structures of the system, such as \texttt{Diary}, \texttt{Trekking}, and \texttt{User}. The Model is independent from the user interface and does not handle user interactions directly.

The \textbf{View} is responsible for rendering the user interface and collecting user input. Its role is limited to presentation and interaction handling, without directly applying business logic or modifying domain data.

The \textbf{Controller} manages the application logic and coordinates the interaction between View and Model. In the adopted variant of MVC, consistent with the interpretation described in both Apple and Oracle documentation, the Controller also plays the role of a \emph{Mediator}. More precisely, the View does not directly manipulate the Model; instead, user actions are forwarded to the Controller, which interprets them, executes the required logic, and updates the corresponding Model data. In this way, the Controller acts as the central coordination point of the interaction, reducing direct dependencies between presentation and domain data.

In addition, the architecture relies on the \textbf{Observer pattern} to keep the user interface consistent with state changes. When the state managed by a Controller is updated, the interested Views are notified through the listener mechanism provided by the Flutter framework, based on ChangeNotifier, integrated via Provider, so that they can refresh their representation accordingly. This notification-based interaction avoids tight coupling and supports consistency across multiple dependent Views.

Therefore, the adopted solution combines the structural organization of MVC with the use of the Mediator pattern in the Controller and the Observer pattern. This combination is particularly suitable for the Flutter-based implementation of the system, where the presentation layer, the application logic, and the domain data remain clearly separated while still cooperating through a well-defined interaction model.



\subsection{ServiceController as a Facade}

The ServiceController is designed following the Facade pattern.

It provides a unified interface that aggregates multiple underlying services, including external APIs and OS-level services. Instead of interacting directly with heterogeneous components, UI components and controllers rely on a single access point.

This design reduces coupling and simplifies the interaction model of the system. It also improves readability and consistency, as all non-domain-specific functionalities are accessed through a centralized component.

Furthermore, the facade allows internal changes to the underlying services without impacting the rest of the application, thus increasing flexibility and maintainability.

\section{Other Design Decisions} \label{Other Design Decisions}

\subsection{Flutter as Application Framework} \label{Flutter as Application Framework}

Flutter was selected for the implementation of the client applications because it provides an effective balance between cross-platform development, interface consistency, and maintainability. A primary requirement of the project was the possibility of deploying the smartphone application on both Android and iOS while preserving the same visual structure and interaction style across platforms. In this respect, Flutter offers a significant advantage, since it enables the development of a single shared codebase while also providing a uniform UI across platforms.

Compared with native alternatives such as Kotlin and Swift, Flutter avoids the need to maintain two separate implementations for Android and iOS, thus reducing duplication of development effort and simplifying maintenance. Compared with other cross-platform solutions, the choice of Flutter was particularly suitable for this project because it supports the construction of a coherent and controlled UI layer, which was important for preserving the same application identity and user experience on both mobile platforms.






\subsection{Firebase as Backend-as-a-Service} \label{Firebase as Backend-as-a-Service}

The adoption of a Backend-as-a-Service solution represents a strategic architectural decision aimed at improving maintainability, scalability, and integration.  \\
Firebase was adopted as the backend solution to support a scalable and robust system architecture while maintaining a clear separation between client-side logic and backend responsibilities. Rather than introducing a custom server-side layer, the system relies on a Backend-as-a-Service approach, where core functionalities are delegated to managed cloud services.

This choice allows the architecture to focus on the coordination of application logic on the client side, while relying on well-established and production-ready services for critical backend responsibilities such as authentication, data persistence, and media storage, integrating with the client applications through platform-specific SDKs.

From an architectural perspective, this approach improves modularity and reduces system complexity by eliminating the need to design and maintain a dedicated backend infrastructure. This approach presents notable advantages, including scalability, reliability, and security, through managed services that are designed to handle distributed workloads and concurrent access patterns.

Furthermore, the use of Firebase aligns well with the multi-platform nature of the system, as both smartphone and smartwatch applications can interact with the same backend services in a consistent and unified manner. This contributes to maintaining a coherent data model across different devices.

















\subsection{Phone Smartwatch Pairing} \label{Phone Smartwatch Pairing}
While the smartphone application directly relies on Firebase Authentication, the smartwatch application does not perform authentication independently. Instead, it adopts a pairing mechanism based on QR code scanning. Through this process, the smartphone securely associates an authenticated user with the smartwatch by storing the corresponding identifier in Firestore. \\
This design choice provides several advantages:
\begin{itemize}
\item avoids handling user credentials on the smartwatch or to enforce specific authentication methods, such as Google Sign-In, reducing the exposure of sensitive data on a constrained and potentially less secure device 
\item simplifies the user interaction model, eliminating the need for credential input on devices where text entry is inherently limited and less user-friendly
\end{itemize}
For these reasons, the interaction is intentionally defined as a pairing process rather than a traditional login, reflecting both its security properties and its role within the overall system architecture. \\









\subsection{OSService Package Design}
\label{OSService Package Design}
As shown in the smartphone component diagram (see Figure~\ref{Mobile Smartphone App component view}), the OSService package has been introduced to isolate all interactions with operating system functionalities and external libraries.

In particular, this package includes the following services:
\begin{itemize}
    \item \texttt{PermissionService}, responsible for handling runtime permissions;
    \item \texttt{GeoService}, responsible for accessing device location;
    \item \texttt{MemoryService}, responsible for local storage and caching;
    \item \texttt{NotificationService}, responsible for managing local notifications;
\end{itemize}

Each service encapsulates the interaction with specific Flutter packages and platform APIs, such as geolocation, local storage, or notification systems. These dependencies correspond to external libraries (e.g., packages available on \textit{pub.dev}) that internally communicate with the underlying operating system.

This design ensures that the rest of the application does not directly depend on platform-specific APIs or external libraries. Instead, all such dependencies are confined within the OSService package.

The main motivation behind this decision is maintainability. If a library or underlying implementation needs to be replaced, only the corresponding service must be modified, without requiring changes in the rest of the system. This significantly reduces the impact of technological changes.

%Moreover, this approach improves testability, as services can be mocked or replaced during testing without affecting higher-level components.

\subsection{Use of External Service Providers}
\label{Use od External Service Providers}

The application relies on a set of external service providers to implement functionalities related to weather information and map visualization, which are required by several functional requirements of the system. 
In particular, these providers support the fulfillment of requirements related to the visualization of weather conditions associated with trekking routes, the detection of weather alerts, and the display of geographical information on maps.

From an architectural perspective, the \texttt{Service\_i} interface acts as the main entry point for all operations involving third-party providers. 
It exposes methods such as \texttt{weather()}, \texttt{forecast()}, \texttt{weatherbitAlerts()}, and map-related operations like \texttt{openTopoMapTile()}.

This design follows a facade-oriented approach: a single interface lets other components access the required functionalities. 
As a result, other components interact only with abstract operations, without depending on the specific provider for the data.
This approach improves modularity and ensures that changes in external services can be handled locally within the service layer, without affecting the rest of the application.
Regarding weather data, two different providers have been adopted based on their respective strengths. 
Standard weather information and forecasts are obtained through OpenWeather, accessed via the \texttt{weather()} and \texttt{forecast()} methods. 
These operations are used to satisfy the functional requirements related to the visualization of current weather conditions and short-term forecasts for trekking locations.

Conversely, weather alerts are handled through Weatherbit, accessed via the \texttt{weatherbitAlerts()} operation. 
This choice is motivated by the availability and reliability of alert-specific data provided by Weatherbit, which are essential to fulfill the functional requirements related to user notification of critical weather conditions. 


Map visualization is supported through external tile providers, such as OpenTopoMap, accessed via dedicated operations in \texttt{Service\_i}. 
These functionalities are required to satisfy the functional requirements related to the visualization of trekking routes and geographical context. 
Delegating this responsibility to external providers avoids the need to manage map data internally and significantly reduces system complexity.







Alternative solutions were considered during the design phase. 
A first option consisted in adopting a single weather provider for both standard weather data and alerts. 
However, this approach was discarded due to limitations in the quality, availability, or completeness of alert data offered by individual providers. 
In particular, while OpenWeather provides reliable general weather information, its alert coverage is not always sufficient for the requirements of the application.




The chosen solution, based on multiple providers integrated through a unified interface, such as \texttt{Service\_i}, represents a trade-off between flexibility and architectural simplicity. 
It allows the system to leverage the strengths of different providers while keeping responsibilities well separated and interactions with higher level components stable.

Overall, the use of external service providers, combined with the abstraction introduced by the \texttt{Service\_i} interface, enables the system to satisfy the relevant functional requirements while preserving modularity, maintainability, and extensibility of the architecture.

\subsection{Network Connectivity Requirements and smartwatch Platform}

The smartwatch application requires reliable access to internet connectivity in order to provide a complete and consistent user experience. 
In particular, network access is necessary for several core functionalities of the system.

The application relies on external services to retrieve real-time data, such as maps, which are essential for trekking activities. 

Internet access enables communication with backend services and APIs, allowing the application to fetch dynamic content and maintain updated information.

Given these requirements, the choice of Wear OS as the target platform is appropriate and justified. 
Wear OS supports multiple network communication modes, including:

\begin{itemize}
    \item \textbf{Bluetooth connectivity}: allows the smartwatch to access the internet indirectly through a paired smartphone.
    \item \textbf{Wi-Fi connectivity}: enables the device to connect directly to wireless networks, allowing standalone operation in specific scenarios.
    \item \textbf{Cellular connectivity (LTE with eSIM)}: available on selected devices, providing full independence from the smartphone and ensuring continuous connectivity during outdoor activities.
\end{itemize}

This flexibility ensures that the application can operate under different conditions, ranging from smartphone-assisted usage to fully autonomous scenarios. 
In particular, the availability of LTE-enabled devices makes Wear OS especially suitable for outdoor and trekking contexts, where the user may not always have access to their smartphone.



\subsection{Image cache strategy}
\label{Image cache design decision}
A caching mechanism has been introduced to reduce latency in loading images from Firebase Storage. Since images represent one of the most bandwidth-intensive resources in the application, caching them locally significantly improves performance and responsiveness.

This decision is particularly relevant given the geographical separation between the database and storage services, as discussed in Section \ref{Firebase BaaS Management}. By minimizing repeated downloads, the caching layer reduces both latency and network usage.
