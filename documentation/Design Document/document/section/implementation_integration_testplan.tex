\chapter{Implementation and Integration} \label{Implementation and Integration}

\section{Implementation Strategy}
The development of the Triplo application followed an incremental approach, starting from the basic components and then moving to higher level features. This was consistent with the architecture of the system, where the lower level parts support the appl logic and the user interface. \

The implementation did not follow a completely fixed sequence. Some parts were developed in parallel and refined as new features were added. \

The first components developed were the \textbf{model components}. They define the main domain entities of the application, such as \texttt{challengeModel}, \texttt{trekkingModel}, \texttt{UserModel} and \texttt{DiaryModel}. These classes are  the data used by the application and exchanged with the backend. \

The \textbf{controller components} were introduced early in the process. Controllers such as \texttt{languagecontroller}, \texttt{challengecontroller}, \texttt{trekkingcontroller}, \texttt{UserController} and \texttt{DiaryController} were then updated while the related features were added. They were not completed all at once, but evolved together  with the introduction of application features. \

The \textbf{view components} were developed together with the controllers. Pages such as \texttt{GeowatchPage}, \texttt{HomePage}, \texttt{trekkingPage}, \texttt{SettingsPage}, \texttt{LoginRegistrationPage}, \texttt{SearchPage}, \texttt{UserProfilePage} and \texttt{DiaryPage} grew gradually together with the application features. \

The application uses \textbf{service components} to delegate some tasks to  the controllers, so that controllers can stay focused on coordinating the app logic. Services such as \texttt{Background\_service}, \texttt{InternetService}, \texttt{permissionservice}, \texttt{geoservice}, \texttt{memoryservice}, \texttt{notificationservice} and \texttt{authservice} manage specific responsibilities, including permissions, geolocation, local storage, notifications, connectivity and authentication. \

This also makes the code easier to maintain, because changes to integrations can remain limited to the corresponding service.

\section{Integration of Software Components}


After the main components were implemented, the application was assembled progressively. We started developing and integrating the components communicating with the backend and then moved to the interface and external services.

\textbf{Firebase} was integrated together with the controller components. Controllers access Firebase services, such as authentication, database and storage through platform specific SDKs, enabling validation features that rely on the backend from the beginning of the integration process.

The \textbf{view components} were then connected to the controllers while their features were being developed. In this way, each feature could be tested and adjusted before adding more functionality.

External services, such as weather and map providers, were connected later, after the related UI components were available. As these dependencies grew, the application introduced a dedicated \textbf{ServiceController} based on the Facade pattern. This component gives the rest of the application one place to access external APIs and OS-level services, keeping these interactions more organized.

The application also connected \textbf{device-level services} through dedicated service components. These services manage interactions with the operating system, such as permissions, geolocation, notifications and local storage.

The integration process was incremental: core backend functionality was integrated first, followed by user interface components and finally external services and OS interactions.

\section{Testing}

\subsection{Objectives}
The purpose of the tests written for this application is to verify logical correctness of the components and their behavior, both normal behavior and error handling.
In order to test the behavior of components that use backend funcitonalities or external APIs, those functionalities have been mocked through the \textit{Mockito} library, allowing the tests to run offline without the need of a network connection: furthermore, this choice allows to test the application logic independently from the backend and the APIs. \\
The UI, the models and the controller and services funcitonalities are tested using a mixed approach, mostly by the use of unit and widget tests. 
The widget tests are useful in order to verify the correct behavior of the UI, the navigation and response to user input.
The tests of the model components verify the correct behavior of the serialization and deserialization of the objects.
The tests of the controllers verify the bahavior of the application logic without the need of the backend or APIs.

\subsection{Widget Tests}
The widget tests were used to check if the UI interface behaves in the correct way. In this appliaction they are very important, because many pages contain buttons, dialogs and content that changes depending on the app state.
These tests aim to verify if a page is rendered correctly and if the user is moved to the right page in response to the user's taps. 
For example, the tests for the search page on the smartphone application, among the graphical elements of the page, check the search field, the user and trekking filters. 
Other widget tests, like the ones for the settings page or the trekking page, check forms, dialogs, profile actions and screen navigation.
\subsection{Module Tests}
The module tests are used to verify larger parts of the application logic, not only a single small function. In this project, they are mainly used for controllers and services, because these components manage many operations together.
A module test usually checks if one component works correctly when it receives some input and interacts with mocked dependencies. For example, the authentication service tests of the smartphone application verify registration, login, logout, password reset and watch connection procedures, the user controller tests check if the controller updates the internal state correctly after login, profile update or follower actions.
These tests are important because they show if one application module behaves well as a whole, even without using the real backend.

\subsubsection{Model Tests}
The model tests are focused on data structures. Their goal is to verify if the application reads, stores and converts data in the right way.
For example, the tests for the model check constructors, getters, setters, default values and especially the methods \texttt{toMap()} and \texttt{fromMap()}. In many cases the tests also verify what happens if a field is missing, null or written with an old key name.
\subsubsection{Controller Tests}
The controller tests are among the most useful ones in the whole project, because the controllers contain a big part of the application logic.
For example, the trekking controller tests verify trekking loading, search, saved routes. The diary controller tests are used for adding, editing and removing diaries, including some edge cases.




\subsubsection{Service Tests}
These tests are used to validate the service components of the app, dealing with authentication, memory cache, notifications, internet connection, permissions, geolocation and background tasks.
For example, the authentication service tests verify the login and registration flows with mocked Firebase objects. The memory service tests check RAM cache, saved locale values and keys. There are also tests for internet status changes, GPS access and permission handling.


\subsection{User Testing}
User testing represents the final stage of validation, where the application is tested by end users in realistic scenarios. This type of testing focuses on usability, user experience, and overall system behavior in real-world conditions.

\paragraph{Weather Alerts Demo}

For demonstration and testing purposes, weather alert notifications can be manually sent through a POST request to the demo server. This allows developers to simulate alert conditions and verify the correct behavior of the system.

On Windows (PowerShell), the following command can be used:

{\small
\begin{verbatim}
Invoke-WebRequest "https://meteodemoserver.onrender.com/alerts" `
-Method POST `
-UseBasicParsing `
-Headers @{ "Content-Type"="application/json" } `
-Body '[
  {
    "event":"Heavy Snow",
    "severity":"Severe",
    "headline":"Snowstorm",
    "description":"Up to 50cm above 1200m"
  },
  {
    "event":"Low visibility",
    "severity":"minor",
    "headline":"Low visibility",
    "description":"Up to 50cm above 1200m"
  }
]' | Select-Object -ExpandProperty Content
\end{verbatim}
}

On Linux and macOS (bash), the equivalent request can be executed using \texttt{curl}:





{\small
\begin{verbatim}
curl -X POST "https://meteodemoserver.onrender.com/alerts" \
-H "Content-Type: application/json" \
-d '[
  {
    "event":"Heavy Snow",
    "severity":"Severe",
    "headline":"Snowstorm",
    "description":"Up to 50cm above 1200m"
  },
  {
    "event":"Low visibility",
    "severity":"minor",
    "headline":"Low visibility",
    "description":"Up to 50cm above 1200m"
  }
]'
\end{verbatim}
}
A successful request returns the following response:
\begin{verbatim}
{"status":"ok"}
\end{verbatim}
This mechanism is used exclusively for testing and demonstration purposes and does not represent the production workflow of the alert system.
